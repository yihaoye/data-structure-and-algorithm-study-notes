# B/B+ Tree
[B Trees and B+ Trees. How they are useful in Databases](https://www.youtube.com/watch?v=aZjYr87r1b8)  

## 定义
一个 m 阶的 B 树是一个有以下属性的树：
* 每一个节点最多有 m 个子节点
* 每一个非叶子节点（除根节点）最少有 ⌈m/2⌉ 个子节点
* 如果根节点不是叶子节点，那么它至少有两个子节点
* 有 k 个子节点的非叶子节点拥有 k − 1 个键
* 所有的叶子节点都在同一层

另外，B/B+ 树是 bottom-up 构建的（往上一层添加新的根节点而不是普通的树那样往下一层添加新的子节点、但是会往同一层左/右添加新的节点）。  

## 原理
![](./bplustree-animation.svg)  

**怎么查找**  
- **单点查询**（比如找 25）：从根开始，25 落在 20 到 40 之间，就走中间那个指针，到叶子里找到 25。无论找哪个键，都要一直走到叶子，所以每次查询读的节点数都一样，就是树的高度，性能很稳定。
- **范围查询**（比如找 15 到 50）：先像单点查询一样找到 15 所在的叶子，然后顺着叶子链表往右扫，扫到 50 为止，不用再回到上层。这是 B+ 树比 B 树更适合数据库的关键原因。

**怎么插入**  
1. 先找到新键应该放进哪个叶子，插进去，并保持叶子内有序。
2. 如果叶子里的键超过了上限，就把它从中间**分裂**成两个叶子，再把右半边的第一个键**复制**一份到父节点，作为新的分隔键。
3. 如果父节点也因此满了，就继续向上分裂。如果一直分裂到根，就新建一个根，树高加 1。

树只会从根部长高，所以所有叶子始终在同一层，这就是"平衡"的由来。

**怎么删除**  
删除和插入反过来：如果叶子里的键少于下限（一般是半满），就先向相邻的兄弟节点**借**一个键；兄弟也不够借的话，就和兄弟**合并**，同时删掉父节点里对应的分隔键。合并也可能一路向上传，最后树高减 1。

**叶子节点的操作**
- 查询：O(log N) - 树高约 log_m N，每层在节点内二分查找，比较 log₂ m 次，两者相乘里 m 正好约掉，总共约 log₂ N 次比较。前提是节点内用二分查找，不能线性扫描。范围查询：先找到起点所在的叶子，再沿着叶子链表往右扫，不用回到上层。
- 插入和删除：多一个 O(m) - 叶子是有序数组，插入、删除要挪动元素，最坏 O(m)。这是顺序表本身的缺点，避免不了。一般只有一个叶子需要挪动。分裂、合并很少发生，摊下来每次操作引起的分裂或合并是常数级（远小于 1）。所以总成本约为：O(log N) 次比较 + 一次 O(m) 的页内挪动 + O(log_m N) 次 I/O。
  - 为什么能接受？m 是按页大小选的，比如 16KB 一页，能放几百个条目。在这个大小下，一次 memmove 很便宜，对 CPU 缓存也友好，远比多读一次磁盘便宜。选 m 的时候，一边要让树矮、I/O 少，一边要让节点内的操作便宜，页大小正好兼顾了两者。
  - 内部节点的插入、删除也是 O(m)，只在子节点分裂或合并时才会触发，摊下来每次操作远不到一次；最坏情况是一路传到根，总共 O(m * log_m N)。

## 为什么数据库用 B/B+树而不是平衡二叉树呢？
在内存比在磁盘的数据，查询效率快得多。如果树这种数据结构作为索引，那每查找一次数据就需要从磁盘中读取一个节点，也就是说的一个磁盘块，但是平衡二叉树可是每个节点只存储一个键值和数据的，如果是 B 树，可以存储更多的节点数据，树的高度也会降低，因此读取磁盘的次数就降下来，查询效率就快。  

**为什么数据库偏爱 B+ 树**  
- **矮胖**：一个节点通常就是一个磁盘页（比如 16KB），能放几百上千个键。三四层就能装下几千万甚至上亿条记录，所以一次查询只需要读三四次磁盘。
- **内部节点更紧凑**：内部节点不存数据，同样大小的页能放更多键，分叉更多，树就更矮。和 B 树相比，这正是它的优势（B 树的内部节点也存数据）。
- **范围查询和排序很快**：叶子之间有链表，`BETWEEN`、`ORDER BY`、全表顺序扫描都只需要沿着链表走。
- **查询耗时稳定**：每次都要走到叶子，路径长度相同。

简单来说，B+ 树就是一本带多级目录的书：内部节点是目录，只告诉你去哪一页；叶子节点是正文，按顺序排好，一页接着一页。

## B 树 vs B+ 树
* B+ 树非叶子节点上是不存储数据的，仅存储键值，而 B 树节点中不仅存储键值，也会存储数据。innodb 中页的默认大小是 16KB，如果不存储数据，那么就会存储更多的键值，相应的树的阶数（节点的子节点树）就会更大，树就会更矮更胖，如此一来我们查找数据进行磁盘的 IO 次数有会再次减少，数据查询的效率也会更快。
* B+ 树索引的所有数据均存储在叶子节点，而且数据是按照顺序排列的，链表连着的。那么 B+ 树使得范围查找，排序查找，分组查找以及去重查找变得异常简单。

### 2-3 树
2-3 树是 B 树的一种特殊情况：它相当于阶数 m = 3 的 B 树（注意不是 B+ 树），每个节点有 2 或 3 个孩子，存 1 或 2 个键。B 树和 B+ 树都把这个思路推广到了任意阶数 m。实际数据库里的 m 一般是几百到上千，所以树非常矮。B+ 树还在 B 树的基础上加了两点：数据只存在叶子里，叶子之间用链表串起来。

## B 树类 vs 红黑树
**B 树类的平衡看着比红黑树简单**，原因与关键在于：树只从根部长高，不从叶子长高。  
普通二叉搜索树插入新元素时，会在底部挂一个新节点。这样某一条路径变长了，各条路径的深度就开始不一致，所以 AVL 树和红黑树要不断检查"哪里歪了"，再用旋转把形状掰回来。  

B 树换了一个思路：
- 新键不挂新节点，而是塞进已有的叶子里，叶子的宽度可以变，深度不变。
- 叶子满了就分裂成两个，把一个键送到父节点。父节点满了就继续往上送。
- 一直送到根也满了，就新建一个根。树高只在这时候加一，而且是所有路径同时加一。

所以"所有叶子在同一层"这个性质，是这些操作自动保持下来的，不需要另外修。B 树的平衡是严格的深度平衡，红黑树只保证最长路径不超过最短路径的两倍。B 树把"不平衡"转移成了节点宽度的变化，而宽度只要在 [⌈m/2⌉, m] 这个范围内，怎么变都没关系。  
而且历史上红黑树其实是从 B 树推导出来的，红黑树就是 B 树的二叉版本。Bayer 在 1972 年发明了一种数据结构，它是阶数为 4 的 B 树的特例，他称之为"对称二叉 B 树"；1978 年，Guibas 和 Sedgewick 在论文中从它推导出了红黑树。  

那为什么内存里还常用红黑树？主要是实现上的取舍：B 树需要管理长度可变的数组，而红黑树就是普通的二叉树。每个节点大小固定，插入时不用挪动数组，旋转次数也有常数上限。不过**现在内存访问也有缓存层级，B 树在内存里也很有竞争力**，比如 Rust 的 BTreeMap。
