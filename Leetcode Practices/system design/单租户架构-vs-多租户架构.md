# 多租户架构 vs 单租户架构对比
Ref: https://www.cloudflare.com/zh-cn/learning/cloud/what-is-multitenancy/  

## 基本概念
| | 说明 |
|---|---|
| **单租户（Single-tenant）** | 每个客户拥有独立的应用实例和/或独立的数据库，资源完全隔离 |
| **多租户（Multi-tenant）** | 多个客户（租户）共享同一套应用实例，通过逻辑隔离（如 tenant_id）区分数据 |

## 核心对比
| 维度 | 单租户 | 多租户 |
|---|---|---|
| **成本** | 每个客户独立部署，基础设施成本随客户数线性增长 | 共享资源，边际成本低，规模效应明显 |
| **隔离性/安全** | 物理隔离，天然安全，数据泄露风险最低 | 逻辑隔离，依赖代码正确性（如查询忘加 tenant_id 会导致数据泄露） |
| **运维复杂度** | 每个实例独立升级/维护，N 个客户 = N 套环境要管 | 一套代码/环境服务所有客户，升级一次全部生效 |
| **定制化能力** | 容易为单个客户做深度定制（独立分支、独立配置） | 定制化需要做成可配置的功能开关，深度定制成本高 |
| **性能隔离** | 某客户高负载不影响其他客户 | 存在 "吵闹邻居"（noisy neighbor）问题，需要限流/资源配额 |
| **扩展性** | 扩容需要为每个客户单独扩容，自动化难度高 | 整体扩容一次覆盖所有客户，更容易做弹性伸缩 |
| **合规/数据主权** | 容易满足"数据必须物理隔离在某地域"类合规要求 | 需要额外设计（如分区部署）才能满足严格合规要求 |
| **发布/灰度** | 可以逐个客户灰度发布，风险可控 | 一次发布影响所有租户，出问题影响面大，需要更谨慎的灰度策略 |
| **数据库设计** | 每租户一库，schema 可以不同 | 常见方案: 共享库 + tenant_id 字段 / 共享库多 schema / 独立库（见下） |

## 多租户的几种数据库隔离模式（从松到紧）
| 模式 | 说明 | 隔离强度 | 成本 |
|---|---|---|---|
| **共享库共享表** | 所有租户数据在同一张表，靠 `tenant_id` 字段区分 | 最弱 | 最低 |
| **共享库独立 Schema** | 同一数据库，每个租户一个 schema | 中等 | 中等 |
| **独立数据库** | 应用共享，但每个租户单独一个数据库实例 | 较强 | 较高 |
| **完全独立部署** | 实际上退化成单租户 | 最强 | 最高 |

很多 SaaS 公司会做**混合模式**：大部分客户用共享库共享表（便宜），付费更高、合规要求更严的大客户走独立库甚至独立部署（"单租户化" 的多租户，业内常称 **"pod" 架构**或**混合租户模型**）。

## 分片式多租户架构
在多租户架构的基础上，按租户标识（如 workspace_id）把租户分组，分散到多个独立的物理/资源单元（shard）上，而不是所有租户共用同一套数据库/消息队列/服务实例。对外仍然是统一的多租户产品，租户感知不到 shard 的存在。  

## 什么场景选哪种

### 选单租户的场景
- 客户是大型企业，对数据隔离、合规（如金融、医疗、政府）要求极高
- 客户需要深度定制，业务逻辑差异很大
- 客户量少但单客户价值极高（私有化部署、本地化部署常见）
- 例如：银行核心系统、政务系统、大型企业的私有部署 SaaS

### 选多租户的场景
- 面向中小企业/个人的标准化 SaaS 产品，客户量大
- 追求低边际成本、快速迭代、统一运维
- 客户对 "完全物理隔离" 没有强诉求
- 例如：Slack、Notion、大多数 B2B/B2C SaaS 产品

## 一个常被忽视的权衡点
研发效率 vs 运维/安全风险  
多租户最大的隐性成本其实不在基础设施，而在**代码质量要求** — 每一个数据库查询、每一个缓存 key、每一个后台任务都必须严格带上 tenant 隔离逻辑，一旦某处漏掉一个 `WHERE tenant_id = ?`，后果就是**跨租户数据泄露**，这是多租户架构里最常见也最危险的 bug 类型。因此很多团队会在 ORM/中间件层强制加一层 "租户上下文自动注入"，而不是依赖开发者手动记得写。
