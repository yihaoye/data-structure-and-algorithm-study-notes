## 编排和协同
编排（orchestration）和协同（choreography）

**两种方式各是什么**
- **协同**：没有中心协调者。每个服务发布"我这边发生了什么"（事件），其他服务自己决定要不要响应、怎么响应。典型的基础设施是 Kafka 这类消息队列。
- **编排**：有一个中心流程，它知道总共有哪几步，按顺序调用各个服务，记录走到了哪一步，最后给出成功或失败的结论。典型工具是 Temporal、AWS Step Functions。

**核心判断：这件事的"完成"由谁负责？**
- 每个服务只需要在自己的领域里把事情做对，没人需要知道全局是否完成 → **协同**。
- 结果必须对整个系统成立，而且需要确认、甚至证明已经完成 → **编排**。

**具体判断标准**
| 问题 | 偏向协同（消息队列） | 偏向编排（Temporal） |
|---|---|---|
| 消息的性质 | 事实："document 被归档了" | 命令："把这个 org 删掉"、"用户下订单" |
| 生产方要知道谁在消费吗 | 不需要，随时可以增加消费方 | 需要，编排方要逐一调用 |
| 要确认全部完成吗 | 不需要，各自最终收敛 | 需要 |
| 顺序要求 | 同一实体的事件有序即可（按分区） | 跨服务的步骤有先后依赖 |
| 失败处理 | 各自重试、进 DLQ | 整体重试、暂停、人工介入或补偿 |
| 持续时间 | 毫秒到秒级 | 几分钟到几个月，可能要等待或审批 |
| 发起人 | 由业务变化自然触发 | 有明确的发起人 |
| 吞吐量 | 高频、大量的小事件 | 次数少，但每次都重要、步骤多 |

**各自的代价**
- **协同的代价**：整个流程的逻辑散落在各个服务里，没人看得到全貌，排查问题要翻遍所有服务的日志。一旦需要知道"整条链走完了没有"，就会被迫自己建状态表、加超时检查，等于手写了一个编排器。
- **编排的代价**：编排方必须知道所有参与者，每多一个参与者就要改流程代码，耦合集中到了这一个地方。用 Temporal 还有它自己的成本：workflow 代码必须是确定性的；长时间运行的流程改代码要做版本管理；历史记录过长要用 continue-as-new 截断；还要运维集群或者付费用 Temporal Cloud。

**常见误区**
1. **"编排的一致性更强"**：不对。两种方式都是最终一致。Temporal 保证的是执行的持久性：流程不会卡在中间没人知道，最后要么完成，要么明确失败。
2. **"用了 Temporal 就不用管幂等"**：不对。activity 可能被执行不止一次，被调用的接口仍然要幂等。消息队列的消费方也一样。
3. **用事件链拼流程**：A 发事件，B 处理完再发事件，C 再接着处理...，流程定义散落各处，难以维护。
4. **什么都用编排**：如果只是"别人变了，我跟着更新"，用编排反而会让编排方要知道所有下游，耦合方向就反了。
5. **把传输和流程混为一谈**：消息队列负责把消息可靠地送到，还能重放；编排负责保存流程状态、推动流程往下走。两者不在同一个层面，经常一起用。

**两种方式都要处理的问题**
- **幂等**：重复执行不能出问题。
- **双写**：先改数据库、再发消息或启动 workflow，这两步不是原子的。消息队列通常用 outbox 模式解决；Temporal 可以用固定的 workflow ID 重试启动，或者让 workflow 的第一步去写数据库。
- **去重**：Temporal 用固定的 workflow ID（比如 `org-delete-{orgID}`）就能保证同一实体只有一个流程在跑；消息队列要自己用状态表加锁来实现。

**实际系统里常常组合使用**
- **事件触发 workflow**：收到一个重要事件，启动一个 workflow 去把事情做完。
- **workflow 发出事件**：流程完成后发一个领域事件，比如"org 已删除"，让不需要参与编排的下游自己响应。
- **workflow 中途接收事件**：用 signal 推进流程，比如审批通过的事件到达后，流程继续往下走。
- **按"是否必须参与"分层**：必须完成、而且有顺序的步骤放进编排；可以随时加入或退出、做不做都不影响结论的，交给事件。

**对照常见系统**
- **订单的核心流程用编排**：只有核心那一段（下单 -> 锁库存 -> 支付 -> 确认订单 -> 发货）是编排，外围部分（订单状态一变比如已支付，会有很多下游关心，但它们做不做、做没做完，都不影响订单本身的结论，比如发短信、推送邮件、大数据处理、审计等等）通常是协同，编排也不一定要用 Temporal，协同式的 Saga 也确实有人在用，也是 Saga 的经典例子。
- **org 删除用 Temporal**：这是命令，有发起人，步骤有先后，必须确认删干净，可能持续很久，正是编排的典型场景。
- **日常依赖变化用 Kafka 加 reconcile**：这是事实，没人需要知道全局是否完成，每个服务自己收敛，reconcile 作为兜底，正是协同的典型场景。

一个实用的信号：如果发现自己在消息队列旁边建了一张表，用来跟踪"这个流程走到哪一步了"，那就该考虑编排了。

**总结**
> 结果只需要在各自领域内成立时，用事件解耦；结果必须对整个系统成立、而且需要确认时，用编排把这种避免不了的耦合集中、显式地放在一个地方。
