# 康威生命游戏
康威生命游戏是一个图灵完备的 zero-player cellular automation。除了二维版本外也有[三维版本](https://tkob-vh.github.io/posts/3d_conway_game/)，这里主要讨论二维版本。  

其中，如果希望产生特定或复杂的行为，初始种子通常需要精心设计。随机种子虽然也能产生丰富的局部结构，但大多数很快就会收敛到全灭或一个稳定状态，或者偶尔进入震荡状态。主要有三种收敛状态：
* 稳定状态（Still Lifes）：较常见，细胞的状态不再变化，或者进入一个稳定的图案。
* 震荡状态（Oscillators）：一般常见，细胞的状态会在有限的几种图案之间循环变化。
* 宇宙飞船状态（Spaceships）：较少见，细胞的状态会在有限的几种图案之间循环变化，并且图案会在空间上移动。

有一些种子设计可以进行长期复杂变化的，比如一些玛土撒拉图案（Methuselah）经过数百甚至数千次迭代后才会稳定并收敛到以上的三种状态的。  

以及比较罕见的状态：
* 无限增长状态（Infinite Growth）：能够无限演化、图案（细胞）规模持续增长.
  * Gosper Glider Gun：最著名的无限增长状态，能够不断地产生宇宙飞船。
  * 图灵机与计算器（Calculators）：利用内部逻辑电路无限输出非循环数列（如圆周率 π、素数），可以是无限非循环（无限非周期）的。
  * 以及 Rakes、Breeder 等等。
  
## 朴素实现
最朴素的是使用二维数组来表示生命游戏的状态，使用循环来更新每一代的状态。但是缺点是空间复杂度和时间复杂度都比较高，尤其是当生命游戏的状态非常大时（即矩阵范围），每轮迭代的时间复杂度为 `O(M)`，M 为所有矩阵格子包括非活跃细胞。因此，可以通过使用稀疏矩阵来表示生命游戏的状态，或者使用哈希表来存储活细胞的位置，从而减少空间复杂度和时间复杂度，每轮迭代时间复杂度为 `O(N)`，迭代 K 轮时间复杂度为 `O(N*K)`，其中 N 为平均活跃细胞：
* [Go 实现](./main.go)
* [Java 实现](./Solution.java)
  
## 工业实现
使用 Bitboard 位级操作来表示生命游戏的状态，在某些场景下更适用（比如网格密度高、有边界固定大小的，但是在无边界或稀疏场景下哈希表仍然更优），每轮迭代时间复杂度仍为 `O(M)`。用二进制位表示每一行，或整个网格打包进若干个 64-bit 整数。  
通常搭配 SIMD/GPU 作为工业场景的实现方案，实际每轮迭代 Wall-Clock Time 是 `O(M/P)`，其中 P 是 CPU/GPU 的并行度（或者可以理解为核心数，P 可以达到上万）。需要注意的是，这只是把总工作量分摊到了 P 个执行单元上，总工作量本身依然是 O(M) 量级，并没有真正减少计算总量。  
  
## HashLife
Ref: https://nolebase.ayaka.io/zh-CN/%E7%AC%94%E8%AE%B0/%F0%9F%9B%A0%EF%B8%8F%20%E5%BC%80%E5%8F%91/%F0%9F%A7%AE%20%E7%AE%97%E6%B3%95/HashLife/HashLife.html  
  
一种压缩空间和时间的算法  
完全不同的范式 — 用四叉树（quadtree）+ 记忆化（memoization）来表示图案，对于大量重复、稀疏或规则结构的图案，可以指数级跳过大量演化步骤（比如直接算出 2^K 步之后的状态，在图案规律性保证缓存有效复用的情况下迭代 K 轮时间复杂度可以达到 `O(logK)`），特别适合模拟超大规模或超长时间的演化（如著名的 Gosper Glider Gun 或复杂图灵机模拟）。  
采用此方案的工程系统包括 Golly - 最权威的 Game of Life 模拟器。但是它不是更好的默认选择，而是针对特定场景（超大规模、高度规律、需要模拟极长时间）的专用工具，并且工程实现要解决垃圾回收、内存膨胀、复杂度陡增等一系列朴素算法根本不需要考虑的问题。
